# `@openstudy/schema`

Canonical StudySet validation and TypeScript types for OpenStudy. This package is the boundary between source-specific data and future persistence or study behavior. It contains no import, progress, persistence, study-mode, or application logic.

## Current schema version

`CURRENT_SCHEMA_VERSION` is `"1.0.0"`. It is the first and only published canonical schema version. The migration registry therefore contains zero production migration steps.

The package release version is separate from the canonical `schemaVersion`.

## Compatibility and strictness

Schema `1.0.0` is the first canonical OpenStudy data-contract version.

- OpenStudy guarantees backward compatibility for supported historical versions: a newer reader must have an explicit parser or deterministic migration path before that historical version is considered supported.
- Forward compatibility is not guaranteed. An older reader does not have to understand a future schema version.
- Unknown future versions are rejected explicitly and are never interpreted heuristically.
- Removing or renaming a serialized field, making an optional field required, tightening validation so a previously valid canonical file becomes invalid, or changing field, identity, or reference semantics requires a major version.
- A backward-compatible additive change, such as adding an optional field, may use a minor version.
- Patch versions must not intentionally change the serialized data contract.

Every canonical object is strict. Zod rejects unknown fields and the generated JSON Schema uses `additionalProperties: false`. Consequently, a `1.0.0` reader may reject a future `1.1.0` document containing an optional field it does not know. This is intentional and consistent with backward compatibility without a forward-compatibility guarantee.

## Canonical shape

```ts
type StudySet = {
  schemaVersion: "1.0.0";
  id: PortableId;
  revision: number; // positive safe integer
  title: string;
  description?: string;
  sources: Source[]; // at least one
  categories: Category[]; // flat and allowed to be empty
  questions: Question[]; // at least one
};
```

`revision` is a positive JavaScript-safe integer representing content revision within one StudySet. Initial content uses revision `1`. Validation does not compare revisions, infer their meaning, or increment them automatically. Schema-only representation changes do not imply a content-revision change. Revision history storage, rollback, branching, and increment rules are outside this package.

Requiring at least one source and one question means a canonical StudySet represents completed, importable, and studiable content rather than an empty draft. Future import and mapping workflows should use separate draft/candidate models instead of weakening the canonical contract to represent incomplete UI state.

## IDs

Internal StudySet, source, category, question, and choice IDs are opaque, stable strings. They:

- are 1 to 128 characters;
- start with an ASCII letter or digit;
- otherwise contain only ASCII letters, digits, `.`, `_`, `:`, or `-`;
- are stored rather than derived from mutable text;
- are validated but never generated by this package.

The contract supports UUIDs, ULIDs, prefixed IDs, and similar generators without requiring one algorithm. Source-system identifiers are stored separately as `externalId` values and are not canonical identity.

## Single-choice questions

```ts
type SingleChoiceQuestion = {
  id: PortableId;
  type: "single-choice";
  prompt: string;
  choices: Array<{ id: PortableId; text: string }>;
  correctChoiceId: PortableId;
  explanation?: string;
  categoryIds?: PortableId[];
  provenance?: QuestionProvenance[];
};
```

Choice IDs must be unique within a question. `correctChoiceId` must reference one of those IDs, so correctness is independent of array order. `QuestionSchema` is a discriminated union with only the V1 `single-choice` member.

## Sources and provenance

Each StudySet declares at least one source:

```ts
type Source = {
  id: PortableId;
  label: string;
  originalFilename?: string;
  externalId?: string;
};
```

The canonical Source deliberately has no format or kind discriminator. JSON, ZIP, DOCX, PDF, CSV, Anki, Moodle, generated material, and future integrations are importer concerns. Adding one of them must not require changing canonical StudySet data. Format-specific details belong in importer or SourceDocument metadata outside this schema.

`Source.externalId`, when present, identifies the contributing source in its own system. It is descriptive source metadata, not canonical Source or Question identity.

A question may cite multiple source contributions:

```ts
type QuestionProvenance = {
  sourceId: PortableId;
  externalId?: string;
  locator?: string;
};
```

`sourceId` is canonical and must reference a declared Source. `QuestionProvenance.externalId` is a source-defined record identifier scoped by `sourceId`; it never becomes canonical question identity. `locator` is an opaque, source-local reference such as `record:182`; the study engine must never interpret it. Richer page, block, or OCR provenance can be added in a future schema without changing core question identity. Raw SourceDocument data is not embedded in StudySet.

## Categories

Categories are a flat top-level registry of stable IDs and labels. Questions reference zero or more IDs. This supports topic filtering and preserves imported sections without introducing hierarchy or taxonomy behavior.

## Validation

```ts
import { StudySetSchema } from "@openstudy/schema";

const result = StudySetSchema.safeParse(unknownData);
```

Zod issues retain paths to the affected fields. The schema rejects duplicate IDs, broken source/category references, invalid discriminators, empty text, and invalid single-choice answers.

## Compatibility and migrations

The public compatibility API separates version detection from canonical validation:

```ts
import {
  detectSchemaVersion,
  migrateStudySet,
} from "@openstudy/schema";

const detection = detectSchemaVersion(unknownData);
const migration = migrateStudySet(unknownData);
```

`detectSchemaVersion` inspects only the top-level object and its own `schemaVersion` field. It distinguishes invalid envelopes, missing or malformed declarations, unsupported historical versions, unsupported future versions, the current version, and future explicitly supported historical versions. It does not first parse input as the current StudySet.

`migrateStudySet` returns a discriminated result rather than throwing for normal compatibility failures. Its error codes are:

- `invalid-input-envelope`
- `missing-schema-version`
- `malformed-schema-version`
- `unsupported-historical-version`
- `unsupported-future-version`
- `missing-migration-path`
- `migration-step-failure`
- `final-canonical-validation-failure`

For `1.0.0`, migration applies zero steps and validates the complete value with `StudySetSchema`. Zod remains authoritative for the final canonical result and all cross-record invariants. Validation returns a new value, does not mutate caller-owned input, and does not add defaults or strip unknown fields.

Production steps live in the explicit table in `src/migration-steps.ts`. Each source version may have only one registered outgoing edge, so dispatch cannot be ambiguous. Path selection follows only those registered edges; semantic-version ordering classifies a declaration as historical or future but never supplies a transformation or allows a version to be skipped.

Migration steps must be pure and deterministic. They must not use time, randomness, locale-sensitive behavior, network or database access, generated IDs, AI, Jev, embeddings, or external services. Representation-only migrations preserve `StudySet.id`, `StudySet.revision`, and all source, category, question, and choice IDs. They never increment the content revision.

Serialized compatibility fixtures are stored by exact version under `test/fixtures/<schemaVersion>/`. No fixture directory is created until that canonical version actually exists.

### Adding a canonical schema version

1. Define the new canonical schema.
2. Add serialized compatibility fixtures for the new version.
3. Implement an explicit previous-version to new-version migration.
4. Register the migration in `src/migration-steps.ts`.
5. Migrate all supported historical fixtures to the current version.
6. Validate every final result against the current Zod schema.
7. Update the supported-version documentation.

A migration is explicit code, not automatic semantic-version conversion. If data cannot be transformed deterministically, the migration must fail.

## JSON Schema

`study-set.schema.json` is generated deterministically with Zod 4's first-party Draft 2020-12 conversion:

```sh
npm run generate:json-schema
```

Consumers can use the package export `@openstudy/schema/study-set.schema.json`.

Standard JSON Schema represents the serialized shape and local field constraints. Zod remains authoritative for cross-record rules such as ID uniqueness and references to existing choices, sources, or categories.
